# 文档整理经验沉淀

## 1. 先找主矛盾，再组织章节

不要直接按原始素材顺序整理。先提炼全文在回答的核心工程问题，再围绕这个问题重排章节。

硬性规则：全文必须串成一条非常明确的主线。不能只是把材料分块摆放；每一章、每一节都要服务同一条解释路径。整理后要检查是否存在叙事线散乱、层次不清、同一点重复解释、或者容易让读者误解的表述。发现这些问题时必须主动修正。

示例：

- 系统提示词架构篇的主矛盾：系统提示词越来越动态，但 prompt cache 需要稳定前缀。
- 行为指令篇的主矛盾：模型天然倾向于多做、快答、泛化和猜测，需要行为指令把它拉回工程边界。

可复用写法：

```text
这篇文章不是在讲 {表层主题}，而是在解释一个工程矛盾：
{A 越来越复杂}，但 {B 要求稳定 / 可控 / 可审查}。
本文会按 {从定义到落地 / 从问题到模式} 的路径展开。
```

## 2. 把源码笔记改成架构叙事

原始笔记通常是“看到什么写什么”，读者会感觉信息很多但线索不强。整理时要把它改成“每一节都回答一个工程问题”。

每节开头先写：

```text
这一层 / 这一模式解决的是 {具体问题}。
```

然后再放源码、例子、分析。

避免一上来就贴代码。先告诉读者为什么这段代码值得看。

## 3. 使用稳定章节模板

对于架构类文章，优先使用：

```text
前言：核心矛盾
第一层：基础抽象
第二层：特殊情况
第三层：边界 / 分流
第四层：下游转换
第五层：完整流程
第六层：优先级 / 决策
约束与陷阱
工程模式总结
对我们的启发
```

对于模式类文章，优先使用：

```text
前言：这些模式共同解决什么问题
模式一
  定义
  源码例子
  为什么有效
  可复用模板
模式二
  定义
  源码例子
  为什么有效
  可复用模板
共同结构
对我们的启发
```

硬性规则：整理文档时必须检查目录结构是否清晰易读。不能只做简单叙事重排；如果原目录层级混乱、编号不贴合主题、章节顺序不利于理解，要主动优化目录。优化后的目录应该让读者只看标题就能理解全文路径。

目录检查标准：

- 标题是否回答“这一节解决什么问题”；
- 章节顺序是否符合读者理解路径；
- 全文主线是否能用一句话说清；
- 同级标题粒度是否一致；
- 是否存在重复章节、跳号、错号；
- 是否存在“源码细节”压过“概念层次”的情况；
- 是否需要把原稿中的小节合并、拆分或前后调整。
- 是否有同一个点在多个章节重复展开；
- 是否有容易让人误解的绝对化、口径不一致或上下文不足的表述。

## 4. 先分层，再讲链路

如果文档里既有概念层次，也有运行时调用链，不要混在一起讲。

推荐顺序：

1. 先讲每一层解决什么问题；
2. 再讲这些层如何串成完整链路；
3. 最后讲约束、模式和启发。

这样读者先理解“零件”，再理解“机器怎么转”。

## 5. 每个概念都要有一句人话定义

不要只保留英文类名或源码名。每个关键对象都补一句人话解释。

示例：

- `systemPromptSection`：解决“提示词段落如何被命名、复用和缓存”的问题。
- `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`：不是给模型看的，而是给缓存分拣逻辑看的分界线。
- `splitSysPromptPrefix`：system prompt 上桌前的分拣器。
- `DANGEROUS_uncachedSystemPromptSection`：必须每轮重算、且需要解释为什么绕过缓存的提示词段落。

## 6. 删除重复解释，把重复内容归位

长文草稿里常见同一个点在多个章节反复出现。整理时要给每个点指定唯一主场。

示例：

- `DANGEROUS_` 的 reason 只在“易变段落”章节详细讲；
- MCP instructions 为什么重算只在对应章节讲，后面表格只引用；
- 缓存命中率陷阱集中放到“缓存优化契约”；
- 工程抽象集中放到“模式总结”。

后文再次出现时，只做短引用，不重新展开。

## 7. 扩展系统文档按生命周期组织，不按模块堆叠

用户反馈 Plugin 系统文档“目录不够清晰，需要语义连贯、保留重点内容，不要冗余”。后续整理 Plugin、Skill、多代理、Hooks 这类扩展系统时，不能简单按源码模块或组件类型罗列章节。

优先使用生命周期主线：

```text
定义边界
  -> 声明 / 契约
  -> 用户意图
  -> 本地物化 / 缓存
  -> 加载 / 拆组件
  -> 运行时激活
  -> 使用边界
  -> 模式总结
```

组件细节要作为某个生命周期阶段的子节出现，而不是和链路阶段并列。比如 Plugin 文档里，commands / skills、agents、hooks 都应该归到“加载时拆成内部组件”，而不是分散成三段独立主线。

## 8. 面向讲解的文档要先翻译术语

用户反馈启动链路文档中“副作用”等术语会让别人看不懂。后续整理面向讲解的架构文档时，不能默认读者理解工程黑话。

写法规则：

- 先讲“它在解决什么痛点”，再给源码名词；
- 遇到 `side effect`、`dynamic import`、`preAction`、`bootstrap`、`prefetch` 这类词，必须补一句人话；
- 如果术语本身不是重点，就直接换成行为描述，比如“模块加载时提前启动的后台读取”；
- 小节标题优先写成问题或动作，不写抽象阶段名；
- 每个阶段都要能被口头复述成一句话。
- 如果用户说“太啰嗦、会跑偏”，不能只替换术语；要重新确认文档终点。比如启动链路的终点不是“CLI 如何启动”，而是“Agent 会话如何拿到运行材料并进入 queryLoop”。外围性能细节、快速出口、预取、Keychain/MDM 等只能作为背景，不应成为章节主线。
- 写 Agent Loop 这类状态机文档时，不能一开始就抛 Continue/Terminal、8 个阶段和大量源码。先给读者一个主分岔：`没有 tool_use -> 收尾/恢复`，`有 tool_use -> 执行工具/next_turn`。等读者抓住这条路，再讲 State、压缩、fallback、hooks 和 token budget。
- 写 Skill 系统这类扩展能力文档时，不能按“来源一节、注册一节、执行一节”堆模块。先讲清楚它的核心矛盾：专业能力很多，但不能把完整 prompt 都塞进每次请求。再按生命周期组织：多来源 -> 统一 Command -> 轻量目录 -> SkillTool 调用 -> inline/fork -> contextModifier -> 压缩恢复。
- 同一组相关文档要统一抽象层级。Plugin 只讲“外部能力包如何进入当前会话”，Skill 只讲“专业指令如何按需进入 Agent Loop”，多代理只讲“任务如何交给子 Agent”。不要在 Plugin 里重讲 Skill/Agent/Hook 内部细节，也不要在多代理里展开完整 queryLoop。

## 7. 图表用于替代占位和长解释

遇到“暂时无法展示”“这里应有图”等占位，不保留原样。改成可渲染内容：

- 流程：用 Mermaid flowchart；
- 决策矩阵：用 Mermaid quadrantChart 或 Markdown 表格；
- 分类对照：用 Markdown 表格；
- 调用链：用 text code block。

图表要服务理解，不要为了装饰而画。

## 8. 保留源码线索，但不让源码打断叙事

源码引用应该帮助读者定位，不应该让文章变成代码摘抄。

硬性规则：用户原稿中已经出现的源码行号、源码片段、英文原代码，整理时必须原样保留。不要改动行号，不要删减代码片段，不要把英文原代码翻译成中文。可以在代码前后增加解释、表格或图示，但不能改变原始代码与行号本身。

推荐写法：

```text
源码位置：
- `src/constants/prompts.ts`
```

如果某段代码很关键，再贴精简片段。贴代码前先说明它在链路中承担什么职责。

## 9. 用“为什么有效”提升文章含金量

仅仅解释源码做了什么不够。每个模式都要回答：为什么这种写法对模型有效？

常见分析角度：

- 反面案例比抽象原则更容易遵循；
- 数字锚点比“简洁”这类形容词更稳定；
- 双边约束能压住两个极端行为；
- `NEVER + unless` 同时提供强约束和明确例外；
- 冗余强化能覆盖长上下文里的注意力盲区；
- 显式解决矛盾指令比让模型自行推理更可靠。

## 10. 结尾要沉淀成可复用方法

不要只做内容总结。最后要告诉读者这套设计如何迁移到自己的系统。

推荐结尾结构：

```text
这套设计给我们的启发是：
1. {实践一}
2. {实践二}
3. {实践三}
4. {实践四}
5. {实践五}

一句话总结：
{把本文核心对象串成一条完整判断}
```

## 11. 验证清单

整理完成后必须检查：

- 章节编号是否连续；
- 是否残留 `TODO`、`暂时无法展示`、错误编号；
- Markdown 代码块是否成对闭合；
- Mermaid 是否在合理位置；
- 同一个概念是否重复解释过多；
- 全文是否串成一条明确主线；
- 层次是否清楚，是否先概念后链路再启发；
- 是否修正了容易误解的表述；
- 章节标题是否足够直白；
- 目录结构是否清晰易读，是否需要主动优化；
- 是否有“源码笔记感”太重的问题；
- 是否有“观点很满但没有源码线索”的问题。

## 12. 下次复用提示

当用户要求“继续整理一篇类似文档”时，直接采用以下工作流：

```text
1. 先读用户原稿，提炼核心矛盾。
2. 确定文档类型：架构类 or 模式类。
3. 写入 todo.md，明确输出路径和验证项。
4. 核对关键源码位置，避免只凭原稿改写。
5. 保留原稿中的源码行号、源码片段和英文原代码，不翻译、不删减、不改写。
6. 检查原目录结构是否清晰易读；不满足则主动优化目录。
7. 检查全文主线是否明确；不明确则先重写主线再落章节。
8. 按模板重组章节。
9. 删除重复解释和占位内容。
10. 修正容易误解的表述。
11. 用 Mermaid / 表格补足图示。
12. 检查章节、目录、主线、占位、代码块闭合。
13. 更新 todo.md 结果复盘。
```

## 13. 分享前发给读者的文档要避免讲者旁白

当用户要求整理“分享前发给工程师看的文档”时，正文必须站在读者视角，而不是讲者备课视角。

避免出现这类表达：

```text
分享时可以这样讲
缓存也值得讲，但不需要讲太深
如果时间不够，优先讲
推荐时间分配
课上可以穿插
```

推荐改法：

- 时间分配、讲解策略、取舍建议放到单独讲稿或备注，不放进发给读者的正文；
- 正文章节用“工程启发”“核心实现逻辑”“进一步阅读”等读者视角表达；
- 对内容深浅的取舍直接反映在正文篇幅和章节层级里，不写成“这里不用讲太深”。

## 14. “Claude Code 怎么做”不能只写抽象机制

面向工程师的分享文档里，`Claude Code 怎么做` 这一节需要给读者一个具体链路，否则容易变成概念列表。

推荐结构：

```text
先用 2-4 句话说核心做法
再给一个缩小版例子
最后点出对应实现角色或运行时对象
```

示例要做到：

- 能把抽象概念落到一轮真实任务或一条真实装配链路上；
- 不需要贴完整源码，但要出现关键实现角色，例如 `getSystemPrompt`、`queryLoop`、`splitSysPromptPrefix`；
- 对缓存、压缩、安全这类抽象能力，要说明输入、分流、输出分别是什么；
- 避免只写“它有 A/B/C 三层”，要补上“这三层如何接力”。

## 15. 示例化源码结构必须标清“源码名”和“解释名”

当文档用缩小版列表解释源码结构时，必须明确它是：

- 逐字源码片段；
- 近似源码结构；
- 还是人话解释映射。

如果列表里混用了源码函数名、section 名和解释性别名，读者会误以为全部来自源码。推荐写法：

```text
下面不是逐字源码，而是按源码角色整理后的近似结构。
```

并在列表后补一句：

```text
`getSimpleIntroSection` 是源码函数名；`session_guidance` 是 section 名；`xxx` 是解释性别名。
```

能用真实函数名和真实 section 名时，优先使用真实名称，不要用 `intro / identity` 这类容易被误认为源码的混合表达。

如果用列表展示近似源码结构，优先给每行补一句短注释，说明它在链路中的职责。这样读者不需要在函数名和 section 名之间来回猜。

示例要放在它解释的具体小节里，而不是放在上层总览里。比如 Prompt Engineering 的“三层结构”属于总览；系统提示词组装示例应该放到“系统提示词分段”小节中，避免总览过重、细节错位。

## 16. 章节统一采用“核心设计 + 示例解释”结构

用户确认 `2.1 系统提示词分段` 的写法是后续章节的目标模式。以后整理分享文档里的每个具体章节时，优先按这个结构组织：

```text
1. 核心设计
   用短段落说明这个模块解决什么问题、核心机制是什么、为什么这样设计。

2. 示例解释
   给一个贴近源码但不过度展开的简化示例。
   示例里可以放少量源码名 / 近似源码结构，并给每行补中文注释。
```

注意：

- 上层“Claude Code 怎么做”只做总览，不堆具体例子；
- 具体例子放到对应小节，例如系统提示词示例放到“系统提示词分段”；
- 示例必须标清“逐字源码”还是“近似源码结构”；
- 示例不要变成大段源码摘抄，重点是让读者看懂核心链路。

## 17. 提出问题后要立刻给 Claude Code 的对应方案

分享稿里如果用问题引出章节，例如“哪些状态要恢复”“为什么需要缓存”“工具结果如何治理”，后面必须尽快接上 Claude Code 的具体方案。

推荐结构：

```text
问题是什么？
Claude Code 用哪几条链路解决？
每条链路解决哪个子问题？
```

避免只抛概念问题却不回答。尤其是 `resume`、`recovery`、`restore` 这类词，要说明具体场景：会话中断恢复、压缩后恢复、运行中错误恢复分别不是一回事。

当一个解释横跨多个机制时，优先单独成小节，而不是硬塞进某个局部章节。比如 `session resume` 和 `post-compact restoration` 同时涉及 Memory、Compression、transcript 和附件机制，适合放在 `Recovery` 小节中统一解释；同时要明确“恢复链路”是机制，不是两个保存文件。

## 18. 先用读者熟悉的概念建模，再落到源码实现

当用户指出某个章节晦涩时，优先判断是否直接跳到了工程实现。比如讲 Memory 时，读者自然会想到工作记忆、情景记忆、长期/语义记忆、程序化记忆。文档应该先用这些熟悉分类建立直觉，再映射到 Claude Code 的工程容器：

```text
工作记忆 -> messagesForQuery / queryLoop State
情景记忆 -> transcript / parent chain
语义记忆 -> CLAUDE.md / memory prompt / system context
程序化记忆 -> system prompt / tool prompt / Skill
外部工作现场记忆 -> FileStateCache / Plan / Delta attachments
```

不要一上来只讲 `mutableMessages`、`FileStateCache`、`bootstrap STATE`，否则读者会觉得是在背源码字段，而不是理解 Agent 的记忆设计。
