FLOW ARROWS  (arrow color = source column color)

A. Orange entry → Runtime:
   - cli.py → AIAgent.run_conversation() (direct)
   - ui-tui/src/ → tui_gateway/server.py (JSON-RPC: prompt.submit) → AIAgent.run_conversation()
   - web/src/ chat → hermes_cli/web_server.py /api/pty → hermes_cli/pty_bridge.py → spawns real hermes --tui; sidecar /api/ws · /api/pub · /api/events for metadata only

B. Purple inbound → Runtime (three sources, one color):
   - B1 Platform adapter (gateway/platforms/…) → gateway/run.py → gateway/session.py → AIAgent.run_conversation() → stream/edit/send back through same adapter.
   - B2 IDE client → acp_adapter/entry.py → acp_adapter/server.py → SessionManager → AIAgent.run_conversation() → session_update chunks back to IDE.
   - B3 cron/scheduler.py tick → cron/jobs.py job → AIAgent.run_conversation(skip_memory=True) inside a dedicated cron session; result is delivered into that cron session (and optionally into a configured gateway recipient via a separate footer frame), NEVER mirrored into a user's main chat transcript.

C. Navy runtime loop (the heart of the diagram):
   AIAgent.__init__ → agent/agent_init.py
   → agent/conversation_loop.py::run_conversation()
     ├─ ensure SQLite session row (hermes_state.py)
     ├─ restore or build cached system prompt
     ├─ run memory prefetch
     ├─ build provider request kwargs
     ├─ invoke plugin pre/post hooks
     ├─ call provider transport (streaming)
     ├─ parse assistant text / reasoning / tool calls
     ├─ if tool calls → dispatch → append tool messages → loop
     └─ until no tool calls OR iteration/budget/interrupt → return final text

D. Green context arrows:
   agent/system_prompt.py + agent/prompt_builder.py build cached system prompt;
   agent/context_references.py expands @file/@folder capsules pre-turn;
   agent/context_engine.py + agent/context_compressor.py + agent/conversation_compression.py compress history when over budget (may rotate active session id).

E. Cyan memory arrows (only for non-cron turns):
   Before first model request of a turn: MemoryManager.on_turn_start() + prefetch_all(); fetched memory is injected ONLY into the outbound API user message, not stored back into the local transcript.
   After final response: _sync_external_memory_for_turn() → sync_all() + queue next prefetch (background, runs at step 14).
   Tool-side hook: memory-provider tool calls re-enter through tool_executor → MemoryManager (see arrow G).
   Cron note: cron-triggered runs pass skip_memory=True by default — they bypass this entire pipeline. Cron's purple arrow (B3) does NOT cross into the cyan Memory column.

F. Teal model arrows:
   agent/chat_completion_helpers.py converts Hermes messages/tools into provider-specific shape via agent/transports/ (chat_completions.py | anthropic.py | bedrock.py | codex.py | codex_app_server.py);
   providers/__init__.py + providers/base.py + plugins/model-providers/* select profile / api_mode;
   streaming deltas flow straight back to UI callbacks.

G. Terracotta tool arrows (dispatch + sandbox execution, Column 6 only):
   Model returns tool calls → agent/conversation_loop.py → agent/tool_executor.py;
   - Agent-level tools (todo, memory, session_search, delegate_task) handled with agent state.
   - Memory-provider tools routed through MemoryManager (cyan, Column 5).
   - skill_* tool calls cross into the Skills column (amber, Column 8) — see arrow L.
   - kanban_* tool calls cross into the Kanban Lane (indigo) — see arrow K.
   - All remaining tools → model_tools.handle_function_call() → tools/registry.py → tool handler running in one of the Column 6 lower-half sandboxes (local / docker / ssh / modal / daytona / singularity terminal, code_execution Python, Chromium camofox, MCP sidecar, file/patch ops).
   Tool results are appended as tool messages and feed back into the next model request.

L. Amber Skills arrows (single-agent knowledge surface):
   - Boot-time / cache-window: agent/system_prompt.py + agent/prompt_builder.py + agent/skill_bundles.py read skills/ + optional-skills/ + the active bundle, then bake the chosen skills into the cached system prompt. This is cache-aware — skills installed mid-session normally take effect NEXT session unless an opt-in --now flag invalidates the cache deliberately.
   - Per-turn slash: /skill <name> inside CLI/TUI/Gateway is intercepted by agent/skill_commands.py and injected as a USER message, NOT a system-prompt mutation. Prompt cache stays valid.
   - Model-driven: tools/skills_tool.py + tools/skill_manager_tool.py are dispatched through Column 6 → tool handler reads/writes SKILL.md under $HERMES_HOME/skills/ and updates tools/skill_usage.py telemetry (.usage.json sidecar).
   - Background: agent/curator.py + agent/curator_backup.py auto-archive stale agent-created skills after step 14 (only skills with provenance "agent" — bundled / hub-installed skills are off-limits).

K. Indigo Kanban arrows (multi-agent task swarm):
   - Dispatcher tick: a long-running loop that, by default, lives INSIDE gateway/run.py (kanban.dispatch_in_gateway=true) and can also run as a standalone systemd unit (plugins/kanban/systemd/). Every kanban.tick_interval seconds it: reclaims stale claims → promotes ready tasks → atomically claims one → spawns a worker AIAgent for the assigned profile with HERMES_KANBAN_BOARD pinned to the board it must work on.
   - Worker runtime: each worker is a normal AIAgent running its own conversation_loop.run_conversation(); its kanban_* tool calls (kanban_show / complete / block / heartbeat / comment / create / link) are dispatched through Column 6 Tool Registry but actually execute against the Kanban Lane's kanban.db.
   - Isolation: Board = hard boundary (HERMES_KANBAN_BOARD env); Tenant = soft namespace inside a board.
   - Failure handling: after kanban.failure_limit consecutive non-success attempts on the same task (default 2), the dispatcher auto-blocks it to break spin loops.
   - Storage split: board / tasks / worker claims live in kanban.db; worker chat transcripts still go into state.db (each worker is a normal AIAgent session).

I. Gray persistence / config arrows:
   run_conversation() incrementally writes transcript state via hermes_state.py into state.db;
   Gateway and ACP keep their own session indexes around the same state.db;
   hermes_cli/config.py + hermes_constants.py + hermes_logging.py provide profile-aware paths, config merge, and rotating logs (agent.log / errors.log / gateway.log).

J. Return arrows (back to the originating surface):
   - CLI: stdout rendering through hermes_cli (spinner + activity feed)
   - TUI: message.delta / message.complete JSON-RPC events
   - Dashboard: raw PTY bytes (chat pane) + sidecar metadata events
   - Gateway: platform-specific send/edit messages
   - ACP: session_update + final assistant message

SEQUENCE MARKERS (1 → 14) — single numeric scheme, no overloaded letters
────────────────────────────────────────
Place small numbered circles along the flow arrows. Each number marks one stage of a single user turn.

1.  Inbound — one of six triggers: CLI text · TUI prompt.submit · Dashboard PTY bytes · Gateway platform event · ACP prompt over stdio · Cron scheduler tick (cron/scheduler.py firing a cron/jobs.py job). Cron is the only trigger that defaults to skip_memory=True at step 5.
2.  Agent resolve — entry resolves provider / model / toolsets / profile and creates or reuses an AIAgent instance (agent_init.py).
3.  Session hydrate — load / create the SQLite session row in state.db; restore prior messages and metadata.
4.  Prompt assemble — cached system prompt (with active skill bundle from Column 8 amber baked in) + expanded @-references + current user message; optional compression. Skill bundle changes default to next-session activation to preserve prompt cache.
5.  Memory prefetch — MemoryManager.on_turn_start() + prefetch_all(); injected only into the outbound API message. SKIPPED entirely when the turn comes from a cron trigger (skip_memory=True).
6.  Provider format — chat_completion_helpers → agent/transports/ picks the right API shape (chat_completions / anthropic / bedrock / codex / codex_app_server).
7.  Model request — request streamed to the selected provider; streaming deltas may go straight back to UI callbacks.
8.  Response parse — runtime normalizes assistant text, reasoning, usage, and tool-call arguments.
9.  Tool dispatch — tool_executor decides:
     - agent-level tool (todo / memory / session_search / delegate_task) → handled inline in agent
     - memory-provider tool → MemoryManager (cyan, Col 5)
     - skill_* tool → Skills subsystem (amber, Col 8) — see arrow L
     - kanban_* tool → Kanban Lane (indigo) — see arrow K
     - everything else → model_tools.handle_function_call() → tools/registry.py
10. Environment execute — selected tool runs in its sandbox in Column 6 lower-half: local/docker/ssh/modal/daytona/singularity terminal, Python code_execution, Chromium (camofox), MCP sidecar, file/patch ops. Skill / Kanban tools execute against the Skills column or Kanban Lane respectively, then return through the same terracotta path.
11. Loop continuation — tool results appended as tool messages; control returns to step 6 until no tool calls OR iteration_budget / max_iterations / interrupt ends the turn.
12. Persist — final messages, usage, session metadata written to state.db; Kanban changes to kanban.db; logs rotated via hermes_logging.
13. Deliver — final assistant response (or interrupt status) returned through the originating surface (CLI / TUI / Dashboard / Gateway / ACP / Cron-session footer).
14. Post-turn — after the user already sees the answer: (a) external memory sync_all() + queued prefetch (cyan, skipped for cron); (b) Skills Curator background pass — agent/curator.py reviews stale agent-created skills, archives via curator_backup.py (amber, Col 8); (c) Kanban dispatcher tick continues independent of this turn, possibly spawning more workers (indigo lane). Cron-triggered turns skip (a) but participate in (c) when configured to enqueue follow-up jobs.
