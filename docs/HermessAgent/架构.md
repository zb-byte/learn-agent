Flow arrows:
- Orange entry arrows: CLI `cli.py` and Ink TUI `ui-tui/src/` accept user input; classic CLI calls `AIAgent.run_conversation()` directly, while Ink TUI sends `prompt.submit` to `tui_gateway/server.py`, which then calls `AIAgent.run_conversation()`.
- Orange dashboard arrows: `web/src/` chat uses `hermes_cli/web_server.py` `/api/pty` to embed the real `hermes --tui` through `hermes_cli/pty_bridge.py`; structured sidebar events use `/api/ws`, `/api/pub`, and `/api/events` as sidecar paths.
- Purple integration arrows: Gateway platform adapters deliver inbound platform events to `gateway/run.py`, which resolves a session with `gateway/session.py`, reuses or creates `AIAgent`, calls `run_conversation()`, then streams/edits/sends the response back through the same platform adapter.
- Purple ACP arrows: IDE clients connect to `acp_adapter/entry.py` over ACP stdio; `acp_adapter/server.py` maps prompts to `SessionManager` / `AIAgent`, calls `run_conversation()`, then returns `session_update` chunks and final messages to the IDE.
- Blue runtime loop arrows: `AIAgent.__init__` delegates setup to `agent/agent_init.py`; `run_agent.py` delegates turns to `agent/conversation_loop.py`, which ensures the DB session, restores or builds the cached system prompt, runs memory prefetch, builds provider request kwargs, invokes pre/post hooks, parses responses, and repeats until final text or interruption.
- Green context arrows: `agent/system_prompt.py` and `agent/prompt_builder.py` build the cached system prompt; `agent/context_references.py` expands explicit @file/@folder style references before the turn where supported; `agent/context_engine.py` and `agent/context_compressor.py` compress oversized conversation history before or during the model loop and may rotate the active session id.
- Cyan memory arrows: `agent/memory_manager.py` receives `on_turn_start()` and `prefetch_all()` before the first model request; fetched memory is injected into the current user message only for the API call; after final response, `_sync_external_memory_for_turn()` calls `sync_all()` and queues the next prefetch.
- Teal model arrows: `agent/chat_completion_helpers.py` builds provider-specific kwargs through `agent/transports/`; provider profiles from `providers/__init__.py` / `providers/base.py` select API mode; requests go to chat completions, Anthropic Messages, Bedrock Converse, Codex Responses, or Codex app-server transport, then normalized responses return to the runtime loop.
- Terracotta tool arrows: model tool calls return to `agent/conversation_loop.py`, which calls `agent/tool_executor.py`; agent-level tools (`todo`, `memory`, `session_search`, `delegate_task`) are handled with agent state, memory-provider tools route through `MemoryManager`, and other tools go through `model_tools.handle_function_call()` to `tools/registry.py`; tool results are appended back into the same conversation loop for the next model request.
- Terracotta Kanban arrows: `tools/kanban_tools.py` exposes Kanban lifecycle tools through the normal tool registry; `hermes_cli/kanban.py` and `hermes_cli/kanban_db.py` manage board/task state and dispatch worker agents; worker state is stored in `kanban.db`, not in the main chat transcript table.
- Gray persistence/config arrows: `run_conversation()` incrementally persists transcript state through `run_agent.py` into `hermes_state.py` `state.db`; gateway and ACP also maintain session indexes around that DB; `hermes_cli/config.py`, `hermes_constants.py`, and `hermes_logging.py` provide profile-aware config, paths, and rotating logs.
- Return arrows: final assistant text and streaming deltas return to the originating surface: CLI terminal rendering, TUI `message.delta/message.complete`, dashboard PTY bytes plus sidecar events, gateway platform messages, or ACP `session_update`.

Sequence markers:
1C CLI entry: `HermesCLI` receives text or slash command; `/command` may stop at `process_command()`, normal chat continues to runtime.
1T TUI entry: Ink composer sends `prompt.submit`; `tui_gateway/server.py` creates or reuses the session agent.
1D Dashboard entry: Web chat opens `/api/pty`, spawning the same `hermes --tui`; sidecar `/api/ws` is for metadata and controls.
1G Gateway entry: platform adapter receives Telegram/Discord/Slack/Feishu/WeCom/Webhook message and `gateway/run.py` resolves the session.
1A ACP entry: IDE sends ACP prompt over stdio; `acp_adapter/server.py` resolves the ACP session.
2R Agent initialize/reuse: entrypoint resolves provider/model/toolsets/config and creates or reuses `AIAgent`.
3S Session hydrate: runtime loads conversation history and restores or creates the SQLite session row.
4C Prompt/context prepare: cached system prompt, explicit references, current user message, and optional compression are assembled.
5M Memory prefetch: `MemoryManager.on_turn_start()` and `prefetch_all()` run; memory context is injected only into the outbound API message.
6O Provider format: `chat_completion_helpers` and `agent/transports/` convert Hermes messages/tools into the selected provider API shape.
7P Model request/stream: request is sent to the selected provider transport; streaming deltas may go straight back to UI callbacks.
8R Response parse: runtime normalizes assistant text, reasoning, usage, and tool-call arguments.
9E Tool dispatch: `agent/tool_executor.py` runs agent-level tools, memory-provider tools, or `model_tools.handle_function_call()` / `tools.registry.dispatch()`.
10E Environment execution: selected tools may run terminal commands, Python/code sandboxes, browser/MCP sidecars, file tools, or Kanban worker dispatch.
11R Loop continuation: tool results are appended as tool messages; runtime returns to provider formatting until no tool calls remain or the budget/interruption ends.
12S State writeback: messages, usage, session metadata, Kanban task state, and logs are written to `state.db`, `kanban.db`, and profile-aware log/config paths as applicable.
13U User update: final response or interruption status is delivered back through CLI/TUI/dashboard/gateway/ACP return path.
14M Post-turn memory: after final response, external memory sync and queued prefetch run in the background; background memory/skill review may start after user-visible delivery.
